# PM能力层赋能建设 - PRD（第一稿）

**文档状态**: Draft  
**需求名称**: PM能力层赋能建设  
**负责人**: 当前产品经理  
**创建日期**: 2026-04-26  
**最近更新**: 2026-04-26  

本 PRD 对应以下 agent 与 tool：

- Agent：`01_agents/角色定义/PRD写作助手.md`
- Tool：`02_tools/模板/PRD骨架模板.md`

## 1. 背景

`pm_agent` 已经具备 `05_drafts/`、`04_workspace/`、`03_context/` 三层结构，能够承接产品知识、进行中工作和临时探索，但仍缺少一层可复用的“能力结构”。

当前问题不是文档没有地方放，而是：

- 面对不同任务时，AI 没有稳定角色
- 每次需求启动都缺少统一输入模板
- 评审、自查、验收缺少固定清单
- “想法 -> 分析 -> PRD -> 沉淀”的链路缺少显式工作流

## 2. 问题定义

### 2.1 当前痛点

- 输出依赖当前提问措辞，稳定性不足
- 需求启动时，关键上下文容易遗漏
- 日常高频 PM 工作缺少统一结构
- 现有三层结构偏内容管理，缺少方法管理

### 2.2 本次需求要解决什么

在不破坏现有仓库结构的前提下，为 `pm_agent` 增加：

- `01_agents/`：角色定义层
- `02_tools/`：模板、清单、工作流层

## 3. 目标

### 3.1 核心目标

- 让 AI 面对不同 PM 工作时有稳定身份
- 让需求分析、原型设计、PRD、纪要、Bug、demo 验收等工作有统一工具结构
- 让新能力层能和 `04_workspace/prd/` 的专题工作方式直接串起来

### 3.2 交付目标

- 新增 `01_agents/`
- 新增 `02_tools/`
- 每层都具备 `README.md`、`AGENTS.md`、`CLAUDE.md`
- 首批至少覆盖 5 个以上高频角色
- 首批至少覆盖模板、清单、工作流三类工具

## 4. 非目标

- 不重命名现有 `03_context/`、`04_workspace/`、`05_drafts/`
- 不建设庞大的全岗位角色库
- 不把专题内容存到 `01_agents/` 或 `02_tools/`
- 不为了模仿文章而复制一套平行目录

## 5. 用户场景

### 场景 1：启动新需求

- 用户先选 `产品策略顾问` 或 `需求分析师`
- 再填写 `需求分析输入卡`
- 输出进入 `04_workspace/prd/某个专题/analysis/`

### 场景 2：编写正式 PRD

- 用户先补齐分析
- 再调用 `PRD写作助手`
- 套用 `PRD骨架模板`
- 输出进入专题 `prd/`

### 场景 3：先出原型说明或 demo 设计

- 用户先调用 `原型设计助手`
- 明确页面结构、交互和关键状态
- 输出进入专题 `prototype/` 或作为 `04_workspace/demos/` 的实现依据

### 场景 4：演示前自查

- 用户调用 `Demo验收助手`
- 套用 `Demo验收清单`
- 产出验收问题清单

## 6. 方案说明

### 6.1 目录方案

```text
pm_agent/
├── 01_agents/
├── 02_tools/
├── 03_context/
├── 04_workspace/
└── 05_drafts/
```

### 6.2 角色方案

首批角色建议：

- 产品策略顾问
- 需求分析师
- 原型设计助手
- PRD写作助手
- 会议纪要整理员
- Bug归因助手
- Demo验收助手
- Context架构师

### 6.3 工具方案

首批工具建议：

- 模板：需求分析输入卡、PRD骨架模板、会议纪要整理模板
- 清单：需求评审检查清单、Demo验收清单
- 工作流：产品需求从想法到沉淀

## 7. 关键流程

### 7.1 标准工作流

1. 用户提出需求或想法
2. 选择合适的 agent
3. 套用合适的 tool
4. 在 `04_workspace/prd/某个专题/analysis/` 产出分析
5. 进入 `prototype/` 与 `prd/`
6. 稳定后提炼到 `03_context/`

### 7.2 目录维护流程

1. 新增角色或工具
2. 同步更新下级 `AGENTS.md` 和 `CLAUDE.md`
3. 如影响根目录职责，回填根目录索引

## 8. 规则与边界条件

- `01_agents/` 只定义“怎么做事”，不存具体业务专题内容
- `02_tools/` 只存结构化工具，不存某次需求正文
- `04_workspace/prd/` 仍是正式需求推进主场
- 如果内容尚未确认，先放 `05_drafts/`
- 已稳定的规则，后续再提炼到 `03_context/`

## 9. 数据与指标

本次需求偏工作方式建设，先以定性指标为主：

- 启动一个新需求时，是否能在 5 分钟内完成结构化输入
- 同类需求输出是否明显更稳定
- 是否减少“补背景、补边界、补待确认项”的反复往返

## 10. 风险与依赖

### 10.1 风险

- 角色过多，导致选择成本上升
- 模板过重，导致实际使用意愿下降
- 新层和旧层职责混淆

### 10.2 依赖

- 依赖使用者持续按新工作流使用
- 依赖索引文件同步维护

## 11. 待确认问题

- 第二批优先补哪些业务型角色
- 是否需要新增“复盘模板”“竞品调研模板”
- 哪些稳定方法应在后续提炼到 `03_context/`
