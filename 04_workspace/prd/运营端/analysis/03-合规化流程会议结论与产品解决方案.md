## 一句话结论

原方案应从“线下医生推荐患者后，平台把同一患者报告回派给该医生解读并结算”调整为“医生端预录入检查建议、患者自主进入平台、后台弱关联匹配、报告查看与服务费结算分离、平台交叉派发报告解读任务并按真实服务记录结算”。

## 原方案的问题

原方案的业务闭环是：

```text
医生推荐患者做检查
  -> 患者通过医生提供的二维码进入平台
  -> 患者支付并完成检查
  -> 平台把该患者报告回派给原推荐医生
  -> 原推荐医生完成解读
  -> 平台向该医生结算报告解读服务费
```

该链路的合规问题在于，推荐、成交、报告回派、结算之间存在明显 1:1 对应关系。即使产品名义上叫“报告解读服务费”，外部也容易理解为医生向平台推荐患者后获得变相开单费。

## 新产品方案

### 1. 前链路改为“医生预录入 + 患者自主进入平台”

目标是弱化医生直接推介痕迹，同时保留患者少填信息、平台自动带入检查建议的效率。

```text
医生端
  -> 录入患者姓名、手机号、身份证、病情描述、检查建议、检查项目、推荐/可选机构
  -> 提交为一条待匹配的检查建议记录

患者端
  -> 通过通用二维码、平台搜索、桌面公共码或其他低指向性入口进入青藤平台
  -> 使用本人手机号/姓名/身份证完成身份识别
  -> 系统自动匹配医生端预录入的检查建议信息
  -> 患者确认检查项目、机构、价格
  -> 支付后进入互联网医院问诊确认和后续检查履约
```

关键规则：

- 不再默认由医生展示个人专属问诊二维码给患者扫码。
- 患者必须用自己的手机完成进入、确认和支付。
- 医生可协助解释检查建议，但产品上不强化“医生直接推荐某机构”的动作。
- 医生端记录和患者端进入通过后台匹配，不在患者面前直接展示强绑定关系。

### 2. 支付链路改为“看清项目和价格后先支付”

目标是保证先收费再履约，同时避免患者产生“一扫码就付款”的不信任感。

```text
患者进入平台
  -> 系统匹配检查建议
  -> 展示检查项目、机构、价格、预约信息
  -> 患者确认
  -> 支付
  -> 互联网医院问诊确认
  -> 到线下交付中心完成检查
```

关键规则：

- 支付前必须展示检查项目、机构和价格。
- 支付后若患者更换机构或项目，通过多退少补、取消重下或补差价解决。
- 平台内可以有两个业务主体，但患者体验上应保持一个平台完成，不要跳来跳去。

### 3. 报告查看与报告解读结算分离

目标是解决医生继续看病需要报告的问题，同时避免把报告回看做成结算依据。

```text
医生自己的患者报告查看
  -> 目的：继续诊疗、完成线下服务
  -> 方式：运营推送报告/影像链接，或患者复诊时出示
  -> 不产生报告解读服务费

平台派发报告解读任务
  -> 目的：医生承接平台委托的报告解读服务
  -> 方式：平台按规则交叉派单
  -> 产生服务记录和服务费
```

关键规则：

- 医生自己的患者是否检查、是否出报告，不通过“待解读任务列表”向医生做对账。
- 医生要看的自己患者报告，可通过现有线下运营方式处理。
- 医生获得服务费，必须对应平台派发且实际完成的报告解读任务。

### 4. 报告解读任务改为交叉派单

目标是打断“医生推荐患者 = 医生解读同一患者 = 医生拿钱”的直接利益链。

```text
报告出具
  -> 系统进入可解读任务池
  -> 根据医生资质、科室、项目类型、区域规则、任务量等做分配
  -> 不把医生自己推荐/预录入的患者报告 1:1 回派给该医生
  -> 医生完成解读服务
  -> 患者查看解读并评价
  -> 平台按服务记录结算医生劳动报酬
```

派单规则初稿：

- 必须打断 1:1 对应：医生解读对象不能直接等于自己推荐成交的患者。
- 跨省不是强制要求：如需可作为后台规则配置，但会议未要求必须跨省。
- 患者信息最小化展示：医生看解读所需的年龄、性别、主诉、检查项目、报告内容即可，姓名、联系方式等应脱敏或隐藏。
- 任务数量与金额可对齐，但产品表达必须是“解读服务量”，不是“推荐成交量”。

### 5. 报告解读页面改造

医生端：

- 列表名称建议从“待解读报告”调整为“报告解读任务”。
- 任务来源表达为平台派发，不表达为“我的患者”或“我推荐的患者”。
- 操作应轻量化，优先支持 AI 生成解读内容，医生确认或少量修改。
- 医生可查看完成记录、服务费汇总和打款记录。

患者端：

- 重点展示解读内容。
- 医生信息可展示，但弱化到服务记录中，不突出个人签名。
- 不做手写签名式强背书。
- 保留一来一回的服务记录和患者评价，证明医生提供了真实服务。

### 6. 医生注册与资质审核

```text
医生本人注册
  -> 填写手机号、真实姓名、身份证、医院、科室、职称、执业证书编号、擅长方向
  -> 上传医师执业证、资格证/职称证、本人证件照等材料
  -> 平台后台审核
  -> 审核通过后进入医生池
  -> 可被分配报告解读任务
```

关键规则：

- 医生应本人登录和提交资料。
- 后台可以审核和补录，但不能替代医生授权。
- 护士、医务工作者等可以存在前链路引导场景，但报告解读必须由具备相应资质的医生承接。

### 7. 结算与收费主体

短期方案：

- 平台定位为撮合平台。
- 采用代收代付口径，先承接患者支付。
- 互联网医院医疗动作通过已有主体解决。
- 向医生支付的是报告解读服务劳动报酬。

长期方案：

- 自有互联网医院牌照拿到后，由互联网医院主体统一收款。
- 互联网医院再向交付中心、平台、医生等进行采购服务或分账。
- 需要同步梳理交付中心协议、开票主体和补充协议。

## 页面改动清单

### 互联网医院诊前问诊专题

- 去掉“医生展示个人二维码，患者直接扫码进入问诊”的强默认链路。
- 增加医生端预录入检查建议记录。
- 增加患者自主进入平台后的身份匹配逻辑。
- 支付页前置展示检查项目、机构、价格。
- 问诊确认和支付顺序需要在 PRD 中重新写清楚。

### 医生报告解读服务专题

- 将“来源医生回流解读”改为“平台交叉派发报告解读任务”。
- 报告解读任务列表不再承载医生自己患者的成交对账。
- 医生自己的患者报告查看不进入服务费结算列表。
- 患者端解读报告弱化医生签名，保留服务记录和评价。
- 医生端服务费汇总以真实解读任务为依据。

### 运营管理与话术

- 增加运营说明手册。
- 运营话术必须避免“开单费”“推荐费”“医生给平台开单”。
- 推荐表达为：平台与医生彼此赋能，医生承接平台委托的报告解读/知识服务，并按真实服务获得劳动报酬。
- 手册输出后先交法务审核。

## 待确认问题

1. 患者入口采用哪些方式并存：通用二维码、搜索平台、短信链接、运营推送、医生口头引导。
2. 医生端预录入后，患者多久未进入平台则记录失效。
3. 交叉派单是否需要考虑跨省、跨机构、跨医生池。
4. 医生可见患者字段的脱敏标准。
5. 患者端是否展示解读医生姓名、职称和机构，展示到什么强度。
6. 医生自己的患者报告查看是否长期依赖运营推送，后续是否做独立非结算入口。
7. CT、MRI 等不同项目的报告解读服务费标准。
8. 自有互联网医院牌照落地后的收款、开票、分账和协议切换节奏。

## 后续 PRD 写法建议

PRD 中不要再使用“开单医生”“回流给来源医生拿服务费”等容易误解的表达。

建议统一术语：

- “线下接诊医生 / 检查建议医生”：描述前链路信息录入角色。
- “互联网医院医生”：描述线上问诊确认角色。
- “报告解读医生”：描述平台派发解读任务的服务承接角色。
- “报告解读服务费”：描述医生完成真实解读服务后的劳动报酬。
- “平台撮合 / 代收代付 / 服务记录”：描述短期合规路径。
