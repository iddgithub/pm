# 检查项目多对多对码 1.0 需求分析

## 记录说明

- 整理时间：2026-06-10
- 当前归属：检查项目多对多对码
- 输入来源：当前会话用户整理稿
- 当前性质：作为独立专题的分析底稿，用于继续产出原型、PRD 和功能清单

## 一句话结论

本需求不是把“一对一对码”改成“字段支持多选”这么简单，而是要把“检查项目标准化、上下游映射、订单组合匹配、异常补配”重构成一套可配置、可追溯、可扩展的底座能力。

## 为什么独立成专题

- 该需求的核心对象是检查项目主数据、上下游映射和订单匹配，不是医生角色链路，也不属于“医生合规开单”主题。
- 上游互联网医院与下游交付中心的项目映射，会复用于多个订单场景，具备独立沉淀价值。
- 后续省份收费规则、套餐定价规则、智能对码推荐，都要建立在这套映射底座之上。

## 当前核心问题

### 1. 上游项目无法被准确标准化

当前平台默认：

```text
一个上游项目 = 一个中心标准项目
```

但实际业务中，上游一个申请单或组合项目，可能同时包含多个部位、多个检查方式或多个检查目标。

典型场景：

- 华西互联网医院传入“颅脑 CT + 胸部 CT + 腹部 CT + 增强”
- 平台实际需要拆解为：
  - `CT-颅脑`
  - `CT-胸部`
  - `CT-腹部`
  - `CT-增强`

如果仍按一对一设计，平台无法识别真实检查内容，也就无法进行后续匹配和下发。

### 2. 下游交付中心项目并不按标准项目逐条维护

当前平台默认：

```text
一个中心标准项目 = 一个交付中心院内项目
```

但交付中心实际维护方式通常更复杂：

- 可能有多部位组合套餐
- 可能有增强加收、第二部位加收
- 可能一个院内项目同时覆盖多个中心标准项目

这意味着下发逻辑不能只做“逐条映射”，而要做“组合覆盖 + 单项补齐 + 加收补齐”。

### 3. 订单下发缺少可追溯的异常闭环

如果项目映射不完整，现有方式容易出现：

- 上游未对码但订单继续流转
- 下游仅匹配部分项目却被误下发
- 多个套餐都能命中，但系统没有优先级判断
- 映射停用后仍被历史逻辑误用

这类问题最终会演变成：

- 订单无法接收
- 检查项目错误
- 费用错误
- 人工排查成本高

## 1.0 版本核心判断

### 1. 本期先做“标准化映射底座”，不做计费规则引擎

1.0 的目标是让订单能被正确识别、正确匹配、正确下发、正确拦截异常，而不是一步到位把价格最优、加收最优、分省最优全部做完。

### 2. 匹配目标是“完整覆盖”，不是“最低价格”

本期匹配策略应优先保证：

- 覆盖上游解析出的全部中心标准项目
- 尽量使用交付中心已有套餐
- 不能完整覆盖时直接拦截

不建议在 1.0 中引入复杂价格最优算法，否则规则边界会显著膨胀。

### 3. 失败必须进入异常池，不能静默跳过

“只匹配成功一部分也先下发”会制造更大业务风险。  
因此本期必须坚持：

- 未完整匹配，不允许直接下发
- 必须记录失败原因、缺失项目、冲突项目
- 支持补配后重新匹配

## 建议的核心数据实体

| 实体 | 说明 | 关键字段 |
| --- | --- | --- |
| 中心标准项目 | 平台唯一的检查项目主数据 | 编码、名称、模态、部位、检查方式、状态 |
| 上游项目映射 | 上游项目到中心标准项目集合的关系 | 上游机构、上游项目编码、上游项目名称、映射标准项目集合、状态 |
| 交付中心项目映射 | 交付中心项目到中心标准项目集合的关系 | 交付中心、院内项目编码、项目类型、覆盖标准项目集合、优先级、状态 |
| 订单匹配执行记录 | 记录订单从解析到下发的全过程 | 订单号、原始项目、标准项目集合、匹配结果、下发项目、耗时 |
| 异常订单记录 | 记录未对码、未匹配、部分匹配等异常 | 异常类型、异常明细、处理状态、处理人、重试结果 |

## 关键业务流程

```text
上游订单进入平台
  -> 读取上游项目对码关系
  -> 解析为中心标准项目集合
  -> 读取目标交付中心项目映射
  -> 按“完全覆盖 > 套餐优先 > 单项目补齐 > 加收项补齐 > 优先级兜底”进行匹配
  -> 生成交付中心可接收项目
  -> 成功则记录匹配日志并下发
  -> 失败则进入异常池，等待补配或人工处理
```

## 1.0 版本范围判断

### 必须纳入

- 中心标准项目库
- 上游项目多对多对码
- 交付中心项目多对多对码
- 单项目 / 组合套餐 / 加收项类型标记
- 订单解析、匹配、下发
- 异常池和匹配日志

### 明确不纳入

- 省份收费规则库
- 完整价格引擎
- 自动最优计费方案
- AI 智能推荐映射
- 复杂审核流和多版本配置回放

## 实施风险

1. 中心标准项目颗粒度如果定义不清，后续映射会持续返工。
2. 交付中心项目类型若缺少统一约束，套餐和加收项容易被随意滥用。
3. 上游项目历史数据可能存在同名不同义，需要批量清洗。
4. 如果异常池没有明确处理责任人，问题会积压。

## 待确认问题

1. “增强”是否独立成标准项目，还是必须依附于某个主项目维护。
2. 组合套餐命中后，是否允许再叠加多个加收项，叠加顺序如何定义。
3. 标准项目是否需要区分“检查内容”和“收费内容”两套口径。
4. 同一个交付中心项目能否同时标记多个类型，1.0 是否允许复合类型。
5. 匹配日志是否只面向运营后台，还是需要向技术支持提供更细的过程明细。
6. 批量导入失败时的回滚方式，是整批失败还是逐条入库并提示错误行。
