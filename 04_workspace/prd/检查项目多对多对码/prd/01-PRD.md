# 检查项目多对多对码 1.0 PRD

**文档状态**: Draft  
**需求名称**: 检查项目多对多对码 1.0  
**负责人**: 待补充  
**创建日期**: 2026-06-10  
**最近更新**: 2026-06-10  

## 1. 背景

当前平台的检查项目对码逻辑主要按“一对一”设计：

```text
上游互联网医院项目 -> 中心平台标准项目 -> 交付中心院内项目
```

该模型默认一个上游项目只对应一个中心标准项目，一个中心标准项目只对应一个交付中心院内项目。但实际业务已经出现以下偏差：

- 上游互联网医院会传入多部位、组合项目或带增强的申请单
- 下游交付中心会维护组合套餐、主项目加收项、第二部位加收项
- 继续用代码硬编码特殊规则，无法支撑机构持续接入和规则扩展

因此需要将现有一对一模式升级为“多对多对码 + 组合匹配下发”的配置化能力。

## 2. 问题定义

- 目标用户：
  - 平台运营配置人员
  - 交付中心对码维护人员
  - 订单运营 / 技术支持人员

- 当前痛点：
  - 上游一个项目无法准确拆解成多个标准项目
  - 下游一个套餐或加收项无法覆盖多个标准项目
  - 订单只能部分匹配时，缺少明确拦截与异常处理闭环

- 现有方案缺陷：
  - 一对一结构限制过强
  - 特殊机构规则依赖代码写死
  - 缺少统一标准项目主数据和匹配日志

## 3. 目标

- 业务目标：
  - 建立统一的中心标准项目库
  - 支持上下游项目灵活映射
  - 提升订单下发成功率和可追溯性

- 用户目标：
  - 运营可自主维护对码关系
  - 订单异常可快速定位和补配
  - 交付中心项目组合能力可被系统识别

- 交付目标：
  - 上游订单可被解析为中心标准项目集合
  - 系统可按交付中心配置生成可接收下发项目
  - 匹配失败时订单进入异常池而非静默失败

## 4. 非目标

- 不在本次范围内的内容：
  - 省份收费规则库
  - 完整计费引擎
  - AI 智能对码推荐
  - 自动最优计费方案

- 暂不处理的边界：
  - 多版本映射回放
  - 复杂审核流
  - 精细化价格优选

## 5. 用户场景

### 场景 1

- 用户角色：平台运营配置人员
- 使用前提：需要接入新的互联网医院项目
- 用户动作：查询上游项目并绑定多个中心标准项目
- 预期结果：系统能将该上游项目解析为标准项目集合

### 场景 2

- 用户角色：交付中心配置人员
- 使用前提：院内项目包含套餐和加收项
- 用户动作：为院内项目设置项目类型、覆盖的中心标准项目和优先级
- 预期结果：订单匹配时系统优先使用可覆盖的套餐和加收项

### 场景 3

- 用户角色：订单运营 / 技术支持
- 使用前提：订单匹配失败或出现冲突
- 用户动作：查看原始项目、解析结果、匹配结果和异常原因，补配后重新匹配
- 预期结果：异常可定位、可修复、可追踪

## 6. 方案说明

- 核心方案：
  - 以中心标准项目库作为唯一主数据底座
  - 上游项目映射到中心标准项目集合
  - 交付中心院内项目映射到中心标准项目集合
  - 订单下发前按规则做组合匹配和完整覆盖校验

- 与现有功能的关系：
  - 保留现有订单下发主链路
  - 替换原有一对一对码假设
  - 为后续收费规则和智能推荐提供结构化基础

- 为什么这样设计：
  - 先解决“识别”和“下发”问题，避免需求被计费规则拖复杂
  - 配置化比硬编码更适合机构持续接入

## 7. 关键流程

1. 用户进入：平台接收上游互联网医院订单。
2. 用户操作：系统读取上游项目对码关系，将原始项目解析为中心标准项目集合。
3. 系统响应：系统读取目标交付中心项目映射关系，按匹配规则生成下发项目。
4. 结果反馈：
   - 完整覆盖则记录日志并下发
   - 未完整覆盖则进入异常池并展示失败原因

## 8. 功能需求

### 8.1 中心标准项目库

- 功能描述：
  - 维护平台统一的标准检查项目主数据
- 输入：
  - 标准项目编码、名称、检查模态、检查部位、检查方式、状态、备注
- 输出：
  - 可被上下游映射引用的中心标准项目
- 校验规则：
  - 标准项目编码唯一
  - 标准项目名称遵循“模态 + 部位 + 检查方式”
  - 停用项目不参与新订单匹配
- 异常处理：
  - 导入失败时提示错误行和错误原因
  - 如已有映射引用停用项目，需提示影响范围

### 8.2 上游项目对码管理

- 功能描述：
  - 将互联网医院项目映射为中心标准项目集合
- 输入：
  - 上游机构、上游项目编码、上游项目名称、映射标准项目集合、状态
- 输出：
  - 上游项目解析规则
- 校验规则：
  - 一个上游项目至少绑定 1 个中心标准项目
  - 可绑定多个中心标准项目
  - 停用映射不参与新订单解析
- 异常处理：
  - 未配置映射的上游项目不得继续下发
  - 重复导入时需提示覆盖或跳过策略

### 8.3 交付中心项目对码管理

- 功能描述：
  - 将交付中心院内项目映射到中心标准项目集合
- 输入：
  - 交付中心、院内项目编码、院内项目名称、项目类型、覆盖标准项目集合、优先级、状态
- 输出：
  - 交付中心项目匹配规则
- 校验规则：
  - 项目类型至少支持：单项目、组合套餐、加收项
  - 组合套餐和单项目允许覆盖重叠，但必须配置优先级
  - 停用映射不参与新订单匹配
- 异常处理：
  - 同一项目缺少项目类型时不可保存
  - 优先级冲突需提示并阻止启用

### 8.4 订单标准化解析与组合匹配

- 功能描述：
  - 将上游原始项目解析为中心标准项目集合，并根据交付中心配置生成下发项目
- 输入：
  - 订单原始项目、上游映射关系、目标交付中心、交付中心映射关系
- 输出：
  - 匹配成功的交付中心项目集合
- 校验规则：
  - 先解析标准项目，再进行下游匹配
  - 必须覆盖全部标准项目才允许下发
  - 避免重复下发同一标准项目对应内容
- 异常处理：
  - 未对码、未匹配、部分匹配、优先级冲突均进入异常池

### 8.5 匹配规则

- 功能描述：
  - 定义 1.0 版本的组合匹配优先级
- 输入：
  - 标准项目集合、交付中心项目映射、项目类型、优先级
- 输出：
  - 最终下发项目集合或异常结果
- 校验规则：
  - 优先级 1：完全匹配优先
  - 优先级 2：组合套餐优先
  - 优先级 3：单项目补齐
  - 优先级 4：加收项补齐
  - 优先级 5：后台优先级兜底
  - 优先级 6：无法完整覆盖则异常
- 异常处理：
  - 命中多个有效方案但无法判断时，进入人工处理

### 8.6 订单匹配日志与异常处理

- 功能描述：
  - 记录订单解析和下发全流程，承接异常补配和重试
- 输入：
  - 订单号、原始项目、标准项目集合、匹配结果、异常类型、处理状态
- 输出：
  - 匹配日志、异常订单池、处理记录
- 校验规则：
  - 每笔订单都要保留原始项目、标准项目、最终下发项目
  - 异常订单必须记录失败原因和处理状态
- 异常处理：
  - 补充对码后支持重新匹配
  - 人工处理应留痕处理人和处理时间

## 9. 规则与边界条件

- 权限规则：
  - 只有具备配置权限的后台用户可新增、编辑、启停映射关系
  - 异常处理支持查看和重试权限分级

- 状态流转规则：
  - 标准项目：启用 / 停用
  - 上游映射：未配置 / 启用 / 停用
  - 交付中心映射：未配置 / 启用 / 停用
  - 异常订单：待处理 / 已补配待重试 / 已处理 / 已关闭

- 数据限制：
  - 一个上游项目可映射多个标准项目
  - 一个交付中心项目可映射多个标准项目
  - 1.0 不支持价格维度参与匹配决策

- 异常场景：
  - 上游项目未对码
  - 下游项目未匹配
  - 部分匹配成功
  - 多个组合冲突
  - 映射已停用

## 10. 数据与指标

- 核心指标：
  - 订单匹配成功率
  - 异常订单占比
  - 异常订单补配后恢复成功率

- 观察指标：
  - 上游未对码项目数
  - 下游未匹配项目数
  - 组合冲突发生次数
  - 平均匹配耗时

- 埋点 / 数据需求：
  - 记录匹配策略命中路径
  - 记录每次重试前后的结果变化
  - 记录配置启停和批量导入操作日志

## 11. 风险与依赖

- 技术依赖：
  - 需要有统一的标准项目主数据结构
  - 需要订单下发链路可接入新的匹配服务

- 产品依赖：
  - 需要明确标准项目颗粒度和命名规范
  - 需要统一项目类型口径

- 运营依赖：
  - 需要运营补齐历史上游和下游映射
  - 需要明确异常池的处理责任人

- 风险点：
  - 标准项目定义不清会导致后续映射持续返工
  - 初期批量导入数据质量可能较差
